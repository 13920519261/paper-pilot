## 一、故障复盘：「每次更新 xpi 后登录信息就丢失」

### 1.1 现象

用户登录后在设置面板看到「✓ 登录成功」，正常使用；一旦安装新版 xpi（Zotero 必然重启），
打开设置面板又变回未登录，需要重新输入邮箱密码。

### 1.2 取证过程

| 证据 | 位置 | 说明 |
|---|---|---|
| 会话文件不存在 | `C:\Users\Administrator\Zotero\paperpilot-account.json` 缺失 | 数据目录里只有 `paperpilot-account.log` / `paperpilot-boot.log`，没有会话文件 |
| 配置目录也没有 | `…\Profiles\swc79sqh.default\` 下无 `paperpilot-account.json` | 双落点全空 |
| 日志全是「找不到」 | `paperpilot-account.log` 20 行，全部 `restore: no session file at any path` | 从未出现过一次 `session saved` |
| 其它模块能写 | `paperpilot-easyscholar.json`、`paperpilot-s2-citations.json` 都在 | 数据目录可写，排除权限问题 |
| 写法唯一不同 | 只有 account.js 用 `IOUtils.writeUTF8(p, t, {mode, tmpPath})`，其余模块都用无选项的 `IOUtils.writeUTF8(p, t)` | 见 §1.3 |
| API 语义 | Zotero 自带 `chrome/content/zotero/osfile.mjs`：`if (options.encoding == 'utf-8') return IOUtils.writeUTF8(path, bytes, options);`；`Archive.worker.mjs` 用 `{ mode: "append" }` | `options.mode` 是**字符串开关** `"append"/"create"/"overwrite"`，不是 UNIX 权限位 |

### 1.3 根因

0.14.0 引入账号系统时，`_save()` 写成了：

```js
await IOUtils.writeUTF8(file, body, { mode: 0o600, tmpPath: file + ".tmp" });
```

`0o600` 是数字（384），而该字段要求字符串枚举 → **该次写入不产出文件**。
更致命的是紧随其后的 `catch`：

```js
} catch (e) {
  Zotero.debug("PaperPilot: account session save failed: " + e.message);   // 只进调试控制台
}
```

**异常被吞掉，`login()` 照常 resolve**，所以界面显示「登录成功」；而磁盘上什么都没有。
下一次启动（对用户而言总是伴随 xpi 更新）`restore()` 自然找不到文件 → 掉登录。

`test/legacy-rootcause.probe.js` 用同一套 mock 加载历史版本代码，把这条链跑成断言：

```
$ node test/legacy-rootcause.probe.js a8daa3e   # 0.14.0 初版
根因取证（参照 a8daa3e）：7 项复现，0 项不符
  ✓ 全部复现：登录成功 ≠ 会话落盘，且失败不可见 → 更新 xpi 后必然掉登录

$ node test/legacy-rootcause.probe.js HEAD      # 0.22.0（用户当前运行的版本谱系）
根因取证（参照 HEAD）：7 项复现，0 项不符
  ✓ 全部复现（该版本已有诊断日志，会记 save FAILED，但写入本身仍未修）
```

### 1.4 为什么前三次修复都没解决

| 版本 | 修了什么 | 为什么不够 |
|---|---|---|
| 0.15.1 | 卸载钩子不再删会话文件；令牌 TTL 7 天→30 天滑动续期 | 会话文件**从来就没被写出来过**，删不删都无关 |
| 0.20.0 | 403 不再误判为会话失效；401 先复核一次；双落点；加 `_diag` 日志 | 仍然没碰 §1.3 的写入本身；只是让失败「有日志可查」 |
| 0.20.0 | `restore()` 本地判过期不再删文件 | 方向对，但文件不存在，无从谈起 |

**结论：症状的成因一直在写入侧，而不是清理侧。** 本版把写入侧彻底重做。

## 二、客户端会话持久化方案（v2 多代冗余仓库）

### 2.1 存储布局

```
<Zotero 数据目录>/           ← Zotero.DataDirectory.dir（本机 = C:\Users\Administrator\Zotero）
  paperpilot-account.json      第 0 代（最新）      ← 旧版单文件即此路径，天然兼容
  paperpilot-account.1.json    第 1 代
  paperpilot-account.2.json    第 2 代
  paperpilot-account.log       生命周期诊断日志（串行写、上限 400 行）
<Zotero 配置目录 ProfD>/       ← 互为兜底的第二落点
  paperpilot-account.json / .1.json / .2.json / .log
```

**最多 6 份会话副本。首次成功登录即写满 6 份**（没有旧代际时用新内容填充 gen1/gen2，
见 `_rollDir(paths, fresh)`），所以「刚登录就出故障」的场景同样有 2 份以上可恢复。

### 2.2 文档结构（v2 信封）

```jsonc
{
  "schemaVersion": 2,          // 版本信封，v1 文档无此字段
  "app": "paperpilot",
  "token": "pp-…",             // 服务端仅存 sha256 散列
  "expiresAt": 1790000000000,  // 本地毫秒时间戳（与服务端 30 天滑动对齐）
  "user": { "email": "…", "name": "…", "plan": "Pro",
            "membership": { "plan": "Pro", "expiresAt": "…", "daysLeft": 88 } },
  "savedAt": 1787000000000,    // 代际排序依据（核心）
  "reason": "login"            // login / refresh / touch / redeem / membership-refresh
}
```

会员信息随会话一起落盘 → **离线也能正确显示等级与到期日**。

### 2.3 写入流程（`_writeDoc`）

对每个落点：

1. **代际滚动**（`_rollDir`）：先读完 gen0/gen1，再 `gen1 ← 旧 gen0`、`gen2 ← 旧 gen1`；
   没有旧代际时用新内容填充（保证首次即有 3 代）。
2. **写第 0 代**（`_writeFile`）：先带 `tmpPath` 原子写（写一半崩溃不留半截文件），
   失败回退**无选项直写**（本插件其余模块长期验证可用的形态）。
3. **回读校验**：写完全文读回比对，`写成功但内容不符`同样判失败，绝不谎报。
4. 全程 `_withTimeout` **硬超时 8s** —— 杜绝「IO 永不 resolve」把登录卡死且无日志。

结果写入 `Account.persistStatus = {attempted, ok, wrote, total, at, errors[]}`。

### 2.4 读取流程（`restore()`）

1. 收集**全部 6 个候选**（落点 × 代际），逐个 JSON 解析；解析失败的**保留现场不删**并记日志。
2. **按 `savedAt` 降序，最新者胜**（取代旧实现的「按路径顺序取第一个就 break」）。
3. 最新副本是 `revoked` 墓碑 → 保持登出（并把其余落点也写墓碑，防止复活）。
4. 否则装载会话；**本地判过期不再直接放弃**，交 `refreshUser()` 的服务端 401 定论
   （首答 401 还会隔 900ms 复核一次）。

### 2.5 登出 / 会话失效 = 墓碑清除（`_wipe`）

关键点：**必须覆盖全部代际**。只删第 0 代的话，第 1/2 代里的旧令牌会在下次启动被读出来，
产生「登出后重启又自动登录」。墓碑文档 `{revoked:true, savedAt, reason}` 同时做到：

- 令牌**物理清除**（磁盘上不再有任何有效令牌）；
- 留下「已登出」的证据，阻止另一落点的残留副本复活会话。

触发场景：用户点「退出登录」、`AIClient` 官方通道 401、`refreshUser` 连续两次 401。

### 2.6 故障与降级矩阵

| 故障 | 行为 |
|---|---|
| 单个落点写失败 | 另一落点照常写；`persistStatus.wrote = 1/2`；登录不受影响 |
| 全部落点写失败 | 本次运行内仍可用（内存会话）；`persistStatus.ok = false`；**设置面板显示橙色告警条**说明「重启后需重新登录」及原因 |
| 第 0 代被删 / 损坏 | 从第 1 代自动恢复 |
| 数据目录整体丢失 | 由 ProfD 落点兜底 |
| 两落点不同步 | 按 `savedAt` 取最新，不再被旧副本遮蔽 |
| 写操作挂起 | 8s 硬超时判定失败并回退，不留静默死锁 |
| 服务端 401 | 复核一次，仍 401 才清会话（且走墓碑） |
| 服务端 403 / 网络异常 | **不清会话**（WAF/反代拦截不代表令牌失效） |

## 三、跨版本迁移策略

### 3.1 客户端（会话文件）

| 起点 | 迁移动作 | 幂等性 |
|---|---|---|
| 无任何文件（本机现状） | 首次登录直接按 v2 写满 2 落点 × 3 代 | 天然幂等 |
| v1 单文件 `{token, expiresAt, savedAt, user}` | `restore()` 直接按兼容字段读取（无 `schemaVersion` 视为 v1）；会话装载后 `refreshUser` 触发的第一次保存把 gen0 升级为 v2，**旧内容原样滚入 gen1/gen2 作为可回滚备份** | 幂等：每次读取都容错，每次写入都滚动 |
| v2 | 无操作 | — |
| 用户在旧代际里手动改过内容 | 不适用（文件仅插件读写） | — |

**回滚路径**：`paperpilot-account.1.json` / `.2.json` 保留了上两代原文，
必要时把 `.1.json` 改名为 `.json` 即可回到上一次会话状态。

### 3.2 服务端（会员数据）

| 数据 | 迁移动作 |
|---|---|
| `users.json`（既有用户） | **不迁移结构**。会员权威信息写在 `user.membership`，`user.plan` / `user.expiresAt` 作为兼容镜像同步维护；旧数据没有 `membership` 字段时，`membershipOf()` 会从 `plan`/`expiresAt` 现场合成视图，`source` 标记为 `legacy` |
| 既有 `Free/Pro/Team` 中的 `Team` | 新体系只保留 `Free`/`Pro`。存量 `Team` 用户在 `membershipOf` 中按 `user.plan` 原样展示，额度取不到配置时回落 Free 额度；管理端下拉不再提供 `Team` |
| `membership.json` | 首次启动用 `newDoc()` 落默认配置；`normalize()` 补齐缺失字段并把 v1 升为 v2（**幂等**，每次启动都安全调用） |
| 每日额度口径变化 | 旧版硬编码 `Free=100 / 非Free=1000`；新版由 `membership.json` 的套餐配置驱动（Pro=3000）。管理员在用户级的 `dailyLimit` 覆盖优先级仍然最高 |

### 3.3 插件升级时的数据边界（为什么不会再丢）

- 会话文件位于 **Zotero 数据目录 + 配置目录**，不在 xpi 内，升级 xpi 不会触碰。
- `bootstrap.js` 的 `uninstall` 钩子**明确不删**会话文件（更新/重装路径会触发 uninstall）。
- 即使某一份被外部清理（同步工具、清理软件、误删），仍有 5 份可恢复。
- 升级后启动日志（`paperpilot-boot.log`）新增一行会话仓库自检：
  `account store: dirs=2 copies=6 newest=数据目录#0 savedAt=… loggedIn=true`
  —— 以后再出现「掉登录」，**第一段启动日志就能给出结论**。

## 四、会员体系

### 4.1 等级与权益（配置化，后台可改）

| 等级 | 每日官方模型额度 | 高级模型 | 价格（默认档位） |
|---|---|---|---|
| **Free** 免费版 | 100 次 | — | 免费，登录即用 |
| **Pro** 专业版 | 3000 次 | ✅ 推理档 / 长上下文 | 1 个月 ¥29 / 3 个月 ¥79 / 12 个月 ¥269 |

- 所有额度、价格档位、权益文案、收款信息都存 `server/data/membership.json`，
  通过 `PUT /api/admin/membership` 修改，**改完即刻生效，不需要重启服务端**。
- 管理员在用户级显式设置的 `dailyLimit` 优先级最高（用于个案调整）。
- 未购买 Pro 的用户不受任何功能门禁限制，只是官方模型额度更低；
  自带 API Key（自有通道）的用户完全不受额度影响 —— 避免「买了才能用」的劝退感。

### 4.2 购买流程（收款码 + 订单核销）

```
插件设置面板                     服务端                       管理员
─────────────                  ─────────                   ─────────
点「升级专业版」
选价格档位 ────────────────► POST /api/orders
                             创建订单(pending)
                             ← 订单号/金额/收款信息
展示订单号 + 收款码
扫码付款
点「我已完成支付」 ─────────► POST /api/orders/:id/claim
                             status: pending → claimed
（面板每 6s 轮询） ◄──────── GET /api/orders/:id
                                                    ► /admin 或启动管理器看到「待核销」
                                                    POST /api/admin/orders/:id/fulfill
                             开通会员 + 生成已用兑换码留档
面板轮询到 fulfilled ◄─────── order.status = fulfilled
自动刷新会员卡片
```

- 订单**绑定下单账号**，核销即自动开通，用户不需要再输任何码。
- 未支付订单 7 天后自动过期（`reapOrders` 惰性回收，列表接口顺带落盘）。
- 核销同时生成一枚**已使用**的兑换码留档，便于对账。

### 4.3 激活方式（两种并存）

| 方式 | 适用场景 | 入口 |
|---|---|---|
| **订单核销** | 插件内自助购买 | 设置面板 → 会员卡片 → 升级专业版 |
| **激活码兑换** | 线下售卖、赠送、补偿、渠道分成 | 设置面板 → 会员卡片 → 「有激活码？」输入框 |

激活码规则：

- 格式 `PP-XXXX-XXXX-XXXX`，字母表剔除易混字符（无 `0 O 1 I L`）。
- 兑换时**大小写与连字符都不敏感**（`pp xxxx xxxx xxxx` 同样识别）。
- 可绑定指定账号（`boundTo`），也可作为通用码；一经使用即绑定使用者。
- 支持 `expiresAt`（活动码有效期），已使用的码不可删除（保留对账记录）。

### 4.4 有效期管理

**续期 = `max(现在, 现有到期) + 时长`** —— 剩余时长不会被吞。

例：Pro 还剩 20 天 → 买 1 个月 → 新到期 = 今天 + 20 天 + 30 天 = 50 天后。

| 场景 | 行为 |
|---|---|
| 到期未续费 | **不踢下线**，`plan` 有效值回落 Free、额度回落 100；插件会员卡片显示红色「已到期」 |
| 剩余 ≤ 7 天 | 会员卡片转警示色「仅剩 N 天 · … 到期」，提示续费 |
| 服务端 `daysLeft` | 由 `/api/auth/me` 与 `/api/membership` 下发，客户端同步落盘，离线可显示 |
| 管理员手改到期日 | 走 `syncMembershipFromLegacy`，**覆盖式**（以填写的日期为准，不叠加）—— 后台手改即最终裁决 |

## 五、API 契约

### 5.1 客户端会用的接口

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/plans` | 公开 | 套餐目录 + 价格档位 + 收款信息 |
| GET | `/api/membership` | Bearer | 当前会员状态（等级/到期/剩余天数/额度/历史） |
| POST | `/api/orders` | Bearer | `{plan, months}` → 下单 |
| GET | `/api/orders/:id` | Bearer | 查询订单（仅本人） |
| POST | `/api/orders/:id/claim` | Bearer | 标记「我已完成支付」 |
| POST | `/api/orders/:id/cancel` | Bearer | 取消未支付订单 |
| POST | `/api/redeem` | Bearer | `{code}` → 兑换并叠加续期 |
| GET | `/api/auth/me` | Bearer | 用户信息（含 `membership`），滑动续期 |

`userForClient()` 现在额外返回：

```jsonc
{ "email": "…", "plan": "Pro", "dailyUsed": 12, "dailyLimit": 3000,
  "membership": { "plan": "Pro", "name": "专业版", "rawPlan": "Pro", "expired": false,
                  "expiresAt": "2027-01-01T00:00:00.000Z", "daysLeft": 88,
                  "dailyLimit": 3000, "source": "order",
                  "activatedAt": "…", "history": [ { "plan": "Pro", "months": 3, "at": "…", "source": "order" } ] } }
```

### 5.2 管理接口（仅本机直连，公网验不到）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/membership` | 订单 + 激活码 + 套餐配置 + 计数 |
| PUT | `/api/admin/membership` | 改套餐额度 / 价格档位 / 收款信息（局部更新） |
| GET | `/api/admin/orders` | 订单列表（含 email、userId） |
| POST | `/api/admin/orders/:id/fulfill` | 核销 → 自动开通 + 生成留档码（幂等） |
| POST | `/api/admin/orders/:id/cancel` | 取消订单 |
| GET/POST | `/api/admin/codes` | 激活码列表 / 批量生成 `{plan, months, count, note, expiresAt?}` |
| DELETE | `/api/admin/codes/:id` | 作废未使用的激活码（已用的不可删） |
| POST | `/api/admin/users/:id/membership` | 直接给用户开通/续期（叠加式） |

`isLocalAdmin()` 判定：回环 socket **且无** `CF-Connecting-IP` / `X-Forwarded-For`
—— Cloudflare Tunnel 回源虽然也来自回环，但必带代理头，因此被正确挡在管理面之外。

## 六、数据存储方案

| 数据 | 位置 | 格式 | 生命周期 |
|---|---|---|---|
| 会话（客户端） | Zotero 数据目录 + ProfD，各 3 代 | JSON（schemaVersion 2） | 30 天滑动；登出/401 走墓碑清除 |
| 账号（服务端） | `server/data/users.json` | scrypt 密码散列 + 令牌 sha256 散列 | 长期；`server/data/` 已 gitignore |
| 会员（服务端） | `server/data/membership.json` | 套餐/价格/收款/订单/激活码 | 长期；订单与已用码为对账记录，不清理 |

**密钥纪律**：任何令牌只出现在 `Authorization` 头，且服务端只存散列；
`server/data/` 不进 git；客户端令牌不进 prefs（回归测试 T11 断言）。

## 七、运维手册

```bash
# 1) 批量生成激活码（10 枚 Pro · 1 个月）
curl -X POST http://127.0.0.1:8000/api/admin/codes \
  -H "Content-Type: application/json" \
  -d '{"plan":"Pro","months":1,"count":10,"note":"线下售卖第一批"}'

# 2) 查看待核销订单
curl http://127.0.0.1:8000/api/admin/orders

# 3) 核销订单（自动开通 + 生成留档码）
curl -X POST http://127.0.0.1:8000/api/admin/orders/<订单号>/fulfill

# 4) 直接给某用户开通 3 个月 Pro（叠加续期）
curl -X POST http://127.0.0.1:8000/api/admin/users/<userId>/membership \
  -H "Content-Type: application/json" -d '{"plan":"Pro","months":3,"note":"补偿"}'

# 5) 调整 Free 每日额度为 150
curl -X PUT http://127.0.0.1:8000/api/admin/membership \
```
